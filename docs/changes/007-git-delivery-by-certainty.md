## 一、用户口径（原话）

> 「我的工作流只需要提交issues和PR，不需要git branch，有修改直接提交进主分支即可。想法、意见等不需要修改的内容都提issues，需要修改就提PR。」

第二轮澄清：

> 「提PR指的是本仓，除非我要求提的PR是外部仓库，否则默认自己的仓库，关于这一点，如果有多个仓库时，你可以进行提问具体的提交位置。不需要git branch指的是你可以用git branch，但是不允许你把修改完成的代码不提交给主分支，却只保留在分支中。即只提交分支，不合并到主分支，也不提PR合并到主分支。分支允许存在，但是不允许过期，已经合并的分支存在。关于PR的定位，确定性路径的修改，即你可以决策完成的修改直接合并到主分支中，不确定性且需要我决策但是已经完成的开发，提及PR等待我完成阅读和合并。」

## 二、落成的口径（四条）

| 改动性质 | 去处 |
| --- | --- |
| 想法 / 意见 / 不需要改内容的 | **issue** |
| **确定性**（可逆 · 仓内 · 不构成豁免，= `§4.0` 决策分派①） | **直接提交并推送 `main`** |
| **不确定性**、需用户裁决，且开发**已完成** | **提 PR**，等用户读后合并 |
| 分支 | **允许存在**（隔离并行 / `worktree` / 已合并的可保留）· **不允许滞留** |

**「不允许滞留」的判据（可机械检查）**：含未合入 `main` 提交的分支，必须**同时**满足其一：
① 有**开放 PR**；② `record.md` 里有**明示的滞留理由与解除条件**。两者都没有 ⇒ 违规。

## 四、为什么这样切（而不是照字面「取消 PR」）

用户原话「不需要 git branch」与「需要修改就提 PR」在**同一处改动**上**结构互斥**——PR 必须有非 `main` 的来源 ref。
第二轮澄清给出了正确分工：**用「确定性」这条已有的判据（`§4.0` 决策分派①）来分流**，而不是取消 PR。

⇒ **这不是新增判据，是把既有判据接到交付路径上**。旧口径（一律走 PR）恰恰**越过了** `§4.0` 已有的分流：
确定性改动也被要求走一遍「开 PR → 自审 → 自合」，PR 沦为形式。

## 五、「不允许滞留」解决的既有问题

issue **#74** 记录的正是这个形态：代码修复 `00f057f` 已提交推送，但**台账条目留在未提交的工作树里**，
读者从 PR 看到 `GAP-047` 却查不到。本规则把「只留分支 / 不落 main」列为违规，
但 #74 的**单条形态（台账行未提交）本规则不覆盖**——那需要 #74 的 DoD 第 2 条（提交引用的 `GAP` 必须在同分支台账可解析）。
