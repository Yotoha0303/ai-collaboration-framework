## 01 设计环 → ADR 落盘 + Schema 迁移带时间戳 + 验收标准可测

| 判据 | 生产里的形态 |
| --- | --- |
| ADR 落盘 | `docs/adr/ADR-NNN-<主题>.md`，**编号连续不重号**，正文含**背景 / 备选 / 取舍**（koliance 实际记到 `ADR-005`） |
| Schema 迁移带时间戳 | 迁移按**序号前缀**排队（`00001_create_product.sql` … 共 12 个），**单一方向、可重放** |
| 验收标准可测 | 每条准出**挂一个可执行的验收动作**（如"部署到 disposable kind 并跑 Saga smoke"），不是"应该没问题" |

> **来源仓的关键做法**：ADR 与 `docs/planning/`（去哪、为什么、接口冻结）**分工**——
> ADR 记**决策**，planning 记**目标**，changes 记**这一步改了什么**（见本文件附录 2「双锚」）。

## 02 开发环 → `docs/changes` 先写后填 + 统一命名

- `docs/changes/NNN-<主题>.md`：**改动前先立记录**，落地后**回填实测**（理由 / 触碰的文件 / 验证命令）。
- **编号是全仓共享且跨分支的**——真实生产里撞过三次（三个 `022`、`030/031`、号顺延两轮）。
  **故选号必须查全部分支的并集**，见 `AGENTS.md` §6.1 与 `.claude/hooks/check-numbers.ps1`。
- **统一命名**：提交信息用约定式前缀（`feat:` / `fix:` / `docs:` / `chore:` / `refactor:`）。

## 03 测试环 → 新用例 100% 入 CI 矩阵 + 覆盖率配置阈值

生产里的**分栈三道 Gate**（来自 `koliance` 的「提交前强制门禁」，**本地先跑，CI 再跑同一套**）：

```bash
# Gate 1：前端 + TypeScript 全套
pnpm type:lint && pnpm test && pnpm build

# Gate 2：合约 + 偿付数学套件
cd contracts && npx tsc --noEmit && npx hardhat test --coverage && npx tsx scripts/check-coverage.ts

# Gate 3：高并发后端
cd ../backend && go vet ./... && go test -race ./...
```

> **可泛化规律（不依赖具体栈）**：**每条准出都要有一个"在本地能跑、在 CI 也跑同一套"的命令**；
> 覆盖率**走配置文件里的阈值**，且读数**取自 LF 工作树**（`AGENTS.md` §5 的 CRLF 教训）。
> **`--race` 不是可选项**：并发正确性**只有**竞态检测器看得见。

## 04 构建环 → 镜像不可变 Digest + `REVISION == Git HEAD`

| 判据 | 生产里的形态 |
| --- | --- |
| 不可变 Digest | 服务镜像用**完整 Commit SHA** 打标签，**记录 OCI Digest 并生成发布清单**；工作流**拒绝覆盖已存在的不可变标签**，并**验证所有 Digest Reference 可访问** |
| `REVISION == Git HEAD` | 发布清单里的 Digest 即**部署时唯一取值**——部署阶段**从清单渲染 Digest**，不再现算 |

> **可泛化规律**：**"不可变"是一个会被验证的断言，不是一句承诺**——
> 「拒绝覆盖」+「验证可访问」是它的**两个负向用例**（D3：不用负向用例证明，等于没有这条规则）。

## 05 部署环 → 全链路幂等 + 配置与环境变量双向对齐

生产里的**自动 CD + 回滚**（`go-order` Phase 8.2）是一条**带证伪的链路**：

```text
部署精确 Digest
  ↓
Readiness + Saga Smoke
  ↓
注入坏镜像            ← 故意注入故障（D3）
  ↓
证明 rollout 失败      ← 断言"坏的必须失败"
  ↓
恢复 Last-Known-Good Digest 集合
  ↓
再次执行 Saga          ← 断言"回滚后必须恢复"
```

> **可泛化规律**：**幂等要被"连跑两次无状态突变"证明，回滚要被"注入坏版本后能回来"证明**——
> 这两条都**不是**靠读脚本判断的（`AGENTS.md` §5「判据不得自审」）。
> 另：`compose`/`Kustomize` 里**必填项用 `${VAR:?required}` 形态**（缺就起不来），比"忘了配"静默跑通安全。

## 06 观测环 → Alertmanager active 区分 + 严重度参与 + 真实停机演练

生产里的**四类故障演练**（`go-order` Phase 8.4，主分支实跑通过）：

| # | 注入什么 | 断言什么 |
| --- | --- | --- |
| 1 | **RabbitMQ 停止** | Worker 会话数 `1→0→1`（**恢复被观测到**，不是"等它自己好"） |
| 2 | **真实慢 HTTP 上游** | 触发**超时 → 开路 → 无网络时拒绝 → 半开恢复**（四个状态**逐段观测**） |
| 3 | **Worker 持租约后被终止** | 第二实例**过期回收**，且**仅完成一次**（**恰好一次**语义） |
| 4 | **非法 Migration** | 在独立 MySQL 中**失败**，且**发布保持阻断**（**该失败的就该失败**） |

> **可泛化规律（本环最重要的三条）**：
> ① **每条告警规则都要有"注入什么能让它响"的用例**——演练 1–4 就是这种用例，不是"测了没问题"。
> ② **"该失败时必须失败"与"该恢复时必须恢复"是两条不同的断言**（演练 2 与 4 分别对应）——
> 只测一边会漏（`AGENTS.md` §8「两道门只跑一道会漏」）。
> ③ **演练后必须再跑一次主流程**（这里的 Saga）——证明"演练没把系统弄坏"，否则全绿是假的。

## 08 恢复环 → 实测 RTO/RPO + **业务级**可用性核验

生产里的**四库备份恢复**（`go-order` Phase 8.3）：

```text
合成业务数据 → 停止写入建立【静止窗口】 → 四库独立 mysqldump
  → 清单：Repository / Commit / UTC / MySQL 版本 / 大小 / SHA-256
  → 独立 MySQL 8.4 容器恢复
  → 校验【迁移状态】+【代表性业务数据】
  → 逻辑 Schema 与主键有序数据指纹 == 源库恢复前指纹（精确一致）
  → 源库恢复后逻辑指纹与恢复前一致
  → 【损坏 Dump 必须被拒绝】          ← 负向用例（D3）
```

> **可泛化规律（三个都容易漏）**：
> ① **"指纹精确一致"**——不是"行数对得上"；**主键有序数据指纹**才能抓住"行数对、内容错"。
> ② **"损坏 Dump 必须被拒绝"**——恢复链路**也要有负向用例**，否则"能恢复"可能只是"没检测到损坏"。
> ③ **"业务级核验"**——数据层对得上**不等于**业务能用；`AGENTS.md` §2 的 08 环准出明确要求业务级用例。
> ④ **RTO/RPO 必须是实测计时**，"计划恢复时间"不是 RTO（D1）。

## 10 自动化环 → 定时器前置条件断言 + 独立归档报告

生产里的形态（`go-order` Phase 8.5，**受保护主分支实跑**）：

| 判据 | 形态 |
| --- | --- |
| 前置条件断言 | 工作流**显式列出并断言**所需前置（`[PREREQUISITE]` 风格）；缺前置**直接失败**，不静默跳过 |
| 独立归档报告 | 压测**出独立报告**：并发阶段 `1/4/8/16/32`、每阶段请求上限 `3000`、**总请求硬上限 `15000`**、实吞吐 `177.989 req/s`、最高 `P95 31.812 ms`、错误数 `0`，以及**首个观测边界**（`concurrency 8` 的吞吐平台与尾延迟增长） |

> **可泛化规律（两条）**：
> ① **报告要有"硬上限"**——上限本身是**前置条件断言**的一种，防止"压测把环境打挂"变成新事故。
> ② **报告要写出"第一个观测到的边界"**，而不只是"通过"——**"通过"不携带信息，"边界在哪"才携带**
> （与 D3 同源：只报"绿"的判据区分不了"正常"与"没测到"）。

## 附：协作规则里的两条（不属十环，但同为本框架的源头）

来自 `koliance` 的**采用实例**，已并入 `AGENTS.md`（见 §3 与 §5）：

1. **执行前文档同步（双锚）**：`docs/planning/` 答"**去哪、为什么、架构规格**"；`docs/changes/` 答
   "**这一步改了什么、怎么验证**"。**两者不可互替**——planning 是罗盘，changes 是足迹。
2. **高频小步提交（量化）**：每个提交应是目标能力的**约 3%** 增量；**每个增量提交前必须过测试**，
   **破提交不得进入历史**；不相关的改动不混进同一提交。
