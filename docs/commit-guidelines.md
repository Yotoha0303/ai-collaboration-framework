# 提交前规范（静态记忆文件）

> **本文件性质**：**按需读取的静态记忆文件**。
> **平时不读取**：日常会话中不常驻加载，不占用上下文窗口（D4 / 体量约束）。
> **触发条件**：**每当要向「AI 协同框架（`ai-collaboration-framework`）」这个仓库提交代码或文档变更时，必须在执行提交动作前强制读取本文件！**
> **约束范围**：约束 AI 总控、所有执行子代理以及项目协作人员针对框架自身的交付行为。

---

## 一、框架核心红线（不可妥协纪律）

### 1. 改动按「确定性」分流：确定则直推 `main`，不确定则提 PR
- **确定性改动**（总控可自行决策的：可逆 · 仓内 · 不构成豁免，判据见 `AGENTS.md` §4.0 决策分派①）
  **直接提交并推送到 `main`**，不必开 PR、不必等评审。
- **不确定性改动**（需用户决策的，且**开发已完成**）**提 PR**，等用户阅读后合并。
  **PR 的定位是「已完成待裁决」的交付物，不是评审闸门**——用户不读，它就停在原地。
- **提交位置**：**默认本仓**。工作区里有多个仓库、或无法确定改动该落在哪个仓时，
  **必须先问用户**，不得按默认值推断（`AGENTS.md` §0.0：位置错不会报错，只会静默地错）。

> ⚠️ **这条已经变过口径（`2026-10-28`）**：此前写的是「**严禁**直接向 `main` 提交或推送，
> 所有变更必须基于 `feat/*` / `fix/*` 分支走 PR」。用户裁定改为**按确定性分流**。
> 变更理由：旧口径要求**每一处**改动都走一遍 PR，在单人高强度掌控的工作流里，
> 确定性改动被拖成"开 PR → 自审 → 自合"，PR 沦为**形式**而不再携带信息。
> 新口径让 PR 重新只在「真的需要人裁决」时出现。

### 1.1 分支允许存在，但**不允许滞留**
- **允许**：用分支隔离并行工作、用 `git worktree` 隔离多会话；**已合并**的分支可以保留。
- **禁止**：改动完成后**只留在分支里**——既不合并进 `main`，也不提 PR。
  这种状态的害处是它**看起来交付了**（提交在、测试绿），而主干上**根本不存在这份能力**。
- **判据（可机械检查）**：任何**含未合入 `main` 提交**的分支，必须**同时满足**其一：
  ① 有对应的**开放 PR**；② `record.md` 里有**明示的滞留理由与解除条件**。
  两者都没有 ⇒ 该分支是**滞留分支**，属违规。

### 2. 有明确的问题，如缺陷和 bug，先提交 issue
- 凡是发现框架自身存在明确的问题、质量缺口（GAP）、文档漂移、安全漏洞或代码逻辑缺陷（Bug），**必须先在 GitHub 仓库提交 Issue 建档**。
- Issue 中必须明确记录：
  1. **问题现象**：实际行为与预期行为的不一致；
  2. **复现与可证伪依据**：终端真实命令、Stdout、退出码或变异测试失败证据（纪律 D1 / D3）；
  3. **根因分析**：底层代码、架构或流程缺陷（5 Whys）；
  4. **整改预期与 DoD**：可量化的修复完成准则。
- 后续创建的 PR **必须明确关联对应 Issue 编号**（例如 `Fixes #xx` 或 `Ref #xx`），做到“无 Issue 不立项，有变更必溯源”。

### 3. 元架构与规则变更必须先与用户讨论确认
- 框架仓的规则源（`AGENTS.md`）、角色契约（`prompts/`、`.claude/agents/`）、守卫逻辑（`hooks/`）与核心台账（`docs/ledger.md`）是所有业务项目的运行底座，属于**系统元架构资产**。
- AI 总控与任何子代理**绝对不得擅自提交或修改框架规则**；遇框架调整需求，必须先向用户提炼分歧点与变更方案，**经人工讨论并获得明确授权后，方可推进**。
- **与第 1 条的关系（必须合读）**：即使某处规则改动对总控而言是「确定性」的，**也不因此获得第 3 条的豁免**——
  「可自行决策」的对象是**实现方式**，不是**要不要改规则**。判据同 `AGENTS.md` §4.0 硬边界 1：
  **门禁与元规则要么满足、要么阻断，没有第三条路**。

## 二、提交前全量规范（静态文本整合沉淀）

> 本节整合原本保存在 `AGENTS.md` §5、`docs/delivery-gates.md` 与工程纪律中的全量提交与交付规范。

### 1. 小步提交量化判据（`AGENTS.md` §5）
- **量级约 3% 增量**：每个提交应是目标能力的约 3% 增量，即“一个可独立说清的逻辑单元”，**严禁把整个模块或多个不相关任务攒成一次大提交**（单笔提交行数失控会导致代码审查疲劳与回滚困难）。
- **过闸**：每个逻辑单元在提交前必须通过对应测试与门禁（§2 的 03 环与本地 Gate），**破提交绝对不得进入 git 历史**（保障 `git bisect` 历史步步可跑）。
- **隔离**：不相关的改动严禁混进同一提交；每个提交必须独立可读、独立可回滚。
- **提交信息清晰规范**：严格遵循 Conventional Commits 格式（`fix:`、`feat:`、`docs:`、`chore:` 等），写清**改了什么、为什么改、怎么验证**（附带正向命令与负向证伪结果）。

### 2. 提交前本地门禁（Local Pre-commit Gates）
- **同一套（本地 = CI）**：本地跑的 Gate 必须与 CI 矩阵完全一致，拒绝“本地绿、CI 红”的无效噪声。
- **`--race` 竞态检测全绿**：对于包含并发逻辑的代码，竞态检测器（Race Detector）是必选项。
- **缺前置即失败**：Gate 必须显式断言前置依赖，缺前置时直接失败阻断，严禁静默跳过（D3 警惕“失败即静默”）。
- **框架自身自测 Gate**：凡改动框架脚本（`.claude/hooks/*.ps1`、`.agents/hooks/*.ps1`）、双语文档（`AGENTS*`、`README*`）或核心台账（`docs/ledger.md`），提交前必须在本地运行自测：
  ```powershell
  powershell -NoProfile -ExecutionPolicy Bypass -File .claude/hooks/self-test.ps1
  ```
  **必须全量通过（PASS = 48 / FAIL = 0，Exit Code 0）方可提交**。

### 3. 推送前四项硬核验（推送四步法）
1. **敏感值扫描**：逐值扫描代码与配置文件，绝对不得将 API Key、Token、私钥或明文密码带入提交。
2. **推送范围核对**：执行 `git status --porcelain` 与 `git ls-files`，核验改动范围仅限本次任务文件，**严禁将框架仓与业务项目仓的文件混淆提交**（§0.0 带项目布局隔离）。
3. **基线冲突预检**：与目标基线分支（`main`）进行预检对齐，确保无分叉与合并冲突。
4. **运行态彻底隔离**：`record.md`（行为留痕）、`memory.md`（上下文状态）、`project-progress.html`（进度展示投影）等运行态文件由 `.gitignore` / `exclude` 严格挡在提交外，绝对不入库。

## 三、触发检查清单（提交前自问自答）

在触发向框架仓提交的最后一刻，总控与执行方必须逐项确认：
- [ ] 本次变更是否已有对应的 GitHub Issue？（想法/意见必提 issue；确定性改动可只留提交级说明）
- [ ] 这次改动是**确定性**（我可自行决策 ⇒ 直推 `main`）还是**不确定性**（需用户裁决 ⇒ 提 PR 等合并）？
- [ ] 若走 PR：提交位置**确定是本仓**吗？多仓时是否已问过用户？
- [ ] 若是规则/台账/角色契约的改动：**是否已取得用户授权**（第 3 条不因第 1 条的「确定性」而豁免）？
- [ ] 有没有**只留在分支里、既不进 `main` 也不提 PR** 的改动？
- [ ] 本地自测与门禁脚本是否全部通过（Exit Code 0）？
- [ ] 提交颗粒度是否保持小步独立（~3% 增量）？
- [ ] 运行态文件是否已完全排除在暂存区外？
