### 案例 001 · 堆叠 PR：母 PR 合并后 base 不会自动改指

- **采集时点**：`2026-10-26T10:10:00Z`
- **适用场景**：在一条**未合并**的分支上再切分支（堆叠 PR）
- **前提**（执行前逐条核对，任一 ✗ 即判不可行）
  - [ ] `gh` 可用且已登录
  - [ ] 能 `git log --oneline <base>..<head>` 列出差额提交
  - [ ] 母 PR 与子 PR 都存在于远端
- **步骤**：
  1. 开子 PR 时 `--base <母分支>`，并在正文**显式写明**「本 PR 堆叠在 #N 上」
  2. 母 PR 合并后：`gh pr edit <子PR> --base main`
  3. 核实：`gh pr view <子PR> --json baseRefName`
- **结果**（真实经历）：`2026-10-26` 建 PR #63 时 base 指向 `fix/c6-dead-predicate`（PR #59，未合并）。
  若不在正文标注、合并后不改指，审阅者会看到一份 diff 含两件事，且子 PR 永远等不到母 PR 的 base 更新。
- **已知边界**：本案例只覆盖「两层堆叠」。三层以上需要逐层改指，顺序不能乱。

### 案例 002 · 已合并分支残留 ⇒ 编号守卫长期报警

- **采集时点**：`2026-10-26T10:15:00Z`
- **适用场景**：`check-numbers` 报「跨分支撞车」，但确信自己没有选错号
- **前提**（执行前逐条核对，任一 ✗ 即判不可行）
  - [ ] `check-numbers.ps1` 可用
  - [ ] 能对每条分支跑 `git ls-tree -r --name-only <ref> -- docs/changes/`
  - [ ] 能 `git merge-base --is-ancestor` 判断祖先关系
- **步骤**：
  1. 对两处 ref 取同一文件的 blob：`git rev-parse <ref>:<path>`
  2. 若 blob **相同** ⇒ 不是内容分叉，是**同一条线上的两个版本**（本地 vs 远端跟踪 ref）
     → 这本已由 `check-numbers` 的分支叶子名折叠处理
  3. 若 blob **不同**且其中一条分支**已合并** ⇒ 是**残留分支**指向合并前的旧内容
     → 删分支属不可逆 ⇒ 登记 `DEFER-`，不自行删
- **结果**（真实经历）：`2026-10-26` PR #56 合并后，`feat/onboarding-first-run` 仍指向 `e6b4256`
  （内容与 `fix/c6-dead-predicate` 的 `267560c` 逐字节相同）⇒ `check-numbers` 持续报 `001` 撞车。
  登记为 `DEFER-016`。
- **已知边界**：若残留分支上真有**未合并**的改动，删它会丢东西——所以必须先比对 blob，再交人裁定。
