# `delivery` · 流程记忆

> **本文件是规则的应用形态，不是规则源**。与 `AGENTS.md` **§5 交付路径**
> 及 `docs/commit-guidelines.md` 冲突时，**以它们为准**（D4）。
> **平时不读**——只在要提交 / 开 PR / 推送时读。

---

## 一、何时用 / 何时不该用

**该用**：任何要写进 git 历史的改动（提交、推送、开 PR、合并后收尾）。

**不该用**：纯运行态更新（`record.md` / `memory.md` / 进度页）——它们不入库，见 `AGENTS.md` §5 入库策略。

---

## 二、流程骨架

### 2.0 前置：确认「你在哪个仓」

```
git rev-parse --show-toplevel
```

一次即可分辨**框架仓**还是**业务项目仓**（`AGENTS.md` §6 多仓归属：两边编号空间互不相干）。

### 2.1 分支

- **不得**直接向 `main` 提交或推送。改动一律走 `feat/*` / `fix/*` 分支。
- **有明确缺陷** ⇒ **先建 issue**，PR 必须关联（`Fixes #N` / `Ref #N`）。
- **元架构 / 规则源变更** ⇒ **先获用户授权**。判据：改的是不是 `AGENTS.md` / `prompts/` /
  `.claude/agents/` / `.claude/hooks/` / `docs/ledger.md`。**是 ⇒ 停下问**。

### 2.2 小步提交（`AGENTS.md` §5 三条量化判据）

| 判据 | 尺度 |
| --- | --- |
| **量级** | 一个提交 ≈ 目标能力的 **3% 增量**——「能独立说清改进的是哪一件事」 |
| **过闸** | 提交前必须过测试；**破提交不得进入 git 历史**（`git bisect` 的前提是步步可跑） |
| **隔离** | 不相关改动不混进同一提交 |

**提交信息**必须写清：**改了什么 · 为什么 · 怎么验证（含证伪结果）**。不接受"看起来对了"。

> ⚠️ **派发子代理时必须在提示词里带上这条**——子代理有全新上下文，不会自己去读 `AGENTS.md` §5。
> 实测：不带这条时，单笔提交 **+1500~3400 行**，正是本条禁止的形态。

### 2.3 推送前四项（**逐项核实，不得假定**）

1. **敏感值扫描**——**逐值比对**，不能只 grep 键名。
2. **推送范围核对**——`git status --porcelain` 与 `git ls-files`；
   确认框架仓与业务仓的文件没混。
3. **与目标基线冲突预检**——`git log --name-only <base> ^HEAD` 求交，再 `git merge-tree` 干跑。
4. **基线对照**——PR 正文给 before/after 表（测试数、覆盖率、地板）。

### 2.4 开 PR

```
git push origin <branch>
gh pr create --base <base> --head <you>:<branch> --title ... --body ...
```

**PR 正文必须含**：改了什么 · 为什么 · **基线与对照** · **负向证伪结果** · **未做（如实）**。

### 2.5 合并后（**最容易被忘的一步**）

- 若 PR 是**堆叠**的（base 不是 `main`），母 PR 合并后**必须** `gh pr edit <本PR> --base main`。
  **基分支不会自动改指**（`GAP-030` 实测）。
- **删除已合并分支**属**不可逆**（改远端 ref）⇒ 若需要，登记 `DEFER-` 交人裁定，**不自行删**。

- 要改规则源（`AGENTS.md` / `commit-guidelines.md`）⇒ 上交总控，**先获用户授权**。
